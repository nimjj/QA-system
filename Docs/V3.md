# App v3

A new grading pipeline in `src/v3/`, switched on with `LAYA_FLOW=v3`. v2 stays the default and is untouched. v3 is built **beside** the frozen v2 files (`laya_inputs.py`, `rule_engine.py`, `laya_windows.py`, the question wording in `dynamic_evaluator.py`); it imports them and never edits them, so the training data and `python laya-finetuning/tools/export_checks.py --check` stay valid.

All numbers below are measured on AI-written calls against AI-written keys, never human-labelled calls. Treat them as "where v3 differs from v2", not "which is right".

**Today v3 grades the same as v2 on the model checks** (same windows, same questions, same cutoffs). On the 100 AG-T calls, 99 had identical results on all 11 items; the one difference was Rapport on `agt_097` (FAIL in v2, PASS in v3). Both flows auto-failed the same 5 calls. v3's gains so far are safety, input handling and service behaviour, not accuracy.

## What v3 changes

* **Built-in criteria, no database.** Every call is graded against the 11 items in `src/v3/config/criteria.json` (two categories, their deductions and weights). `criteria_data` in a request is ignored. v3 never connects to PostgreSQL.
* **Input layer** (`normalise.py`): float, string and `[hh:mm:ss]` times, null sentiment, real `end_time` (v2 assumed every turn lasted 10 s), speaker labels such as `Rep`, `IVR`, `Agent 2`, empty turns dropped, size limits (`config/v3.json`: 1,500 turns, 4,000 characters per turn, 250,000 in all). Too big gives 413, unreadable gives 422.
* **Rules** (`rules.py`): Branding accepts speech-to-text spellings; dead air uses real gaps and excuses announced holds and customer look-ups; Verified no longer accepts "email address"; Personalized matches whole words; auto-fail uses word patterns with an allow-list ("that's not a stupid question" no longer zeroes a call). Verified accepts PIN, security answer and billing address only. Postcode, date of birth and account number are opt-in in `config/v3.json`; that is a business decision still to be made.
* **Scoring** (`scoring.py`): scores by item name against the criteria's own categories, so a different category name can no longer turn penalties into a score of 100.
* **Question marks** (`text.py`): speech-to-text has no "?", so v2's Probing and Active listening saw no questions. v3 restores a "?" on turns that plainly open as questions.
* **Evidence and versions:** each scorecard item can carry `evidence_turns` (turn numbers in the caller's list); the response has `meta` (flow, config version, model, rows and words sent to the model, seconds, warnings).
* **Queue** (`jobs.py`): one worker grades one call at a time. `POST /api/evaluate` waits up to `EVALUATE_TIMEOUT_SEC` (120), then returns 503 with a `job_id` and `Retry-After`. `POST /api/jobs` returns 202 at once; `GET /api/jobs/{id}` returns the result. A full line (`QUEUE_MAX`, 50) gives 503. Transcripts are dropped from memory when grading starts; finished jobs are forgotten after an hour. The model loads at startup (`/ready` is 503 until it has), so a bad checkpoint path fails at startup.
* **API hardening** (`src/api/web_app.py`, also active in v2): request logs hold sizes, not transcript text or customer names (`LOG_REQUEST_BODIES=1` restores them for debugging); requests over `MAX_REQUEST_BYTES` (2 MB) are refused; optional `QA_API_KEY` (send `x-api-key`); `CORS_ORIGINS`; `/health` is liveness only, `/ready` is readiness.

## Run it

```
LAYA_FLOW=v3 python main.py          # with LAYA_CHECKPOINT set in .env as for v2
```
Note: `LAYA_FLOW=v3` makes the shared `flow_version()` fall back to the checkpoint rule (v2 windows with a fine-tuned checkpoint, v1 windows with the stock model).

Tests (no model needed, about a second): `python -m unittest discover -s tests/unit -t .`

With the real model:
* `python Scripts/v3_compare.py inputs/AG-T --out laya-finetuning/runs/v3/compare_agt.jsonl` runs v2 and v3 on every call and lists each differing item (ids only for the sealed-style sets).
* `python Scripts/v3_service_test.py --out laya-finetuning/runs/v3/service_test.json` starts the server, then tests a real request, bad input, a full waiting line, 20 simultaneous requests and a worst-case transcript, and records peak memory (Windows only).
* `python Scripts/golden.py rules` compares the four rule checks of v2 and v3 over all call sets (1 of 330 calls differs).

## Measured results (this PC: Core Ultra 7 255U, 14 threads, 15 GB RAM; checkpoint `final-softce-3`)

Service test, `laya-finetuning/runs/v3/service_test.json`:

| Test | Result |
|---|---|
| Model load | ready after 7.2 s, 1.95 GB |
| 3 real requests | scores equal the offline v3 scores (90.0, 78.3, 68.3); 11 to 16 s each |
| Bad input | empty transcript 422; 3 MB body 413; 1,600 turns 413; unknown job 404; `/health` 200 |
| 56 calls submitted at the same moment (line holds 50) | 51 accepted, 5 refused with 503 and `Retry-After`; all 51 graded, 0 failed; 11.9 s per call overall, so the last call waited about 10 minutes; server healthy afterwards |
| 20 simultaneous `/api/evaluate` | 13 answered within the 120 s wait limit; 7 got 503 with a `job_id` and all 7 finished later |
| Worst case: 1,500 turns, 378 KB | graded in 56 s with 42 model rows and 5,186 words; server stayed up |
| Peak memory over the whole test | 2.72 GB working set, 4.48 GB peak commit (target limit 8 GB). Not run under an enforced 8 GB cap |

Compute: about 13 to 14 model rows and 1,500 words per call, about 12 s per call here; v3 was designed to cost the same as v2. A slower cloud CPU will be slower: plan for 20 to 30 s.

## Known gaps and decisions for the owner

* Accuracy fixes (S4) are the next step. The audit found that the app, not the model, causes most errors: Resolved reads only the last 10 lines; the Ownership phrase gate misses real deflections; Empathy windows often miss the angriest moment; Paraphrasing only looks in the first 5 minutes. Each fix is to be measured alone against v2 and reviewed by a person on a sample of the differing calls.
* Sentiment rules must stay relative to the call: no real transcripts have been available to calibrate an absolute scale. Customer-side sentiment only.
* Verified-customer policy (postcode, date of birth, account number) needs a business decision.
* Not done: Docker image for v3 (no database needed), pinned dependencies, optional faster int8/ONNX model (plain int8 flipped 9 of 12 decisions, so it is not usable as is), job state survives only while the process runs.
* The v2 database code and tenant endpoints are still in the repo for the v2 flow.
