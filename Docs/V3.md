# App v3

A new grading pipeline in `src/v3/`, switched on with `LAYA_FLOW=v3`. v2 stays the default and is untouched. v3 is built **beside** the frozen v2 files (`laya_inputs.py`, `rule_engine.py`, `laya_windows.py`, the question wording in `dynamic_evaluator.py`); it imports them and never edits them, so the training data and `python ../laya-finetuning/tools/export_checks.py --check` stay valid.

All numbers below are measured on AI-written calls against AI-written keys, never human-labelled calls. Treat them as "where v3 differs from v2", not "which is right".

## Accuracy fixes (stage S4)

Method: each candidate window was scored with the real model (`checkpoint final-softce-3`) against the AI-written keys by `../laya-finetuning/eval/v3_gate_lab.py`. Variants and cutoffs were chosen on the **development sets** (AG-T, AG50: 150 calls); the **hold-out sets** (AG-B, AG-B2, AG-C: 112 calls) were then read to confirm. For Resolved the hold-out was read before the final pick among the pre-declared variants, so it is a confirmation with some selection in it, not a clean test. The keys are AI-written, not human-labelled, and the sentiment scores in these calls were written by the same AI, so the mood signal in particular may not transfer to real recordings.

| Check | Change | Result | Decision |
|---|---|---|---|
| **Resolved** | window = the last 16 informative lines (thanks/goodbye lines skipped, final two lines kept, 320 words max); score = 50% model + 50% how the customer ended relative to their own call (mean of last 3 customer sentiments minus the call median); PASS at 0.65. No usable customer sentiment: the model score alone, same cutoff | v2 was close to chance on the hold-out (balanced accuracy 0.52; below chance on AG-B). Blend: 0.78 on hold, 0.75 on dev, flat from cutoff 0.50 to 0.70. Items correct on hold 57 -> 84 of 112 (34 better / 7 worse) | **adopted** (`gates.resolved`) |
| **Ownership** | the window opens on a wider set of deflection wordings ("not ours", "X's responsibility", "cannot be performed", "you must wait", blaming the customer, sending them to a store); the model still decides | v2's gate showed the model almost none of the real deflections on other authors' sets (it caught 1 of 14 in AG-B, 0 of 13 in AG-C); now about half. AUC 0.79 -> 0.92 dev, 0.54 -> 0.70 hold. Items correct on hold: 85 -> 86 of 112 (12 better / 11 worse): it finds faults but also fails more good calls (14% of good calls in AG-B, 8% in AG-C, and 4 of 5 look-alikes in AG-B2) | **adopted** with that trade-off (`gates.ownership`) |
| Paraphrasing | cue phrases anywhere in the call, plus any agent line the customer answers with "yes/exactly" that reuses the customer's words (`cue_aff`) | Better on AG-T (balanced accuracy 0.69 -> 0.84, where 30 true restatements had no v2 cue), worse on AG50 (0.86 -> 0.72) and slightly worse on hold (0.95 -> 0.93; 3 better / 5 worse). The AG50 losses are partly near-verbatim echoes that the key calls FAIL | **not adopted**; v2 stays. Switch: `gates.paraphrasing.mode = "v3"`. A person should review the ~12 disputed calls |
| Empathy | trigger relative to the call's own sentiment (`rel_first`, `rel_deep`) instead of a fixed -15 | Found more outbursts (91% of the keyed unhandled ones against 68%) but more windows per call made the model fail many more good calls: good calls kept on hold 0.65 -> 0.26 to 0.32 | **not adopted**; v2 stays |
| Rapport | not changed (it is the model's best check and needs the full scan) | | |

* The one rule difference (`agc_42`, Dead air) counts against v3 here only because the key for rule items was computed with v2's code, which assumed every turn lasts 10 s; v3 uses the call's real end times.
* Cost is unchanged: 9 to 13 model rows and 1,100 to 1,600 words per call.
* Still weak and model-limited (candidates for retraining, S5): Empathy (strict, many false fails), Active listening, Resolved (the model alone is only AUC 0.6 to 0.8), and Probing/Rapport errors that no window change touched.

## What v3 changes

* **Built-in criteria, no database.** Every call is graded against the 11 items in `src/v3/config/criteria.json` (two categories, their deductions and weights). `criteria_data` in a request is ignored. v3 never connects to PostgreSQL.
* **Input layer** (`normalise.py`): float, string and `[hh:mm:ss]` times, null sentiment, real `end_time` (v2 assumed every turn lasted 10 s), speaker labels such as `Rep`, `IVR`, `Agent 2`, empty turns dropped, size limits (`config/v3.json`: 1,500 turns, 4,000 characters per turn, 250,000 in all). Too big gives 413, unreadable gives 422.
* **Rules** (`rules.py`): Branding accepts speech-to-text spellings; dead air uses real gaps and excuses announced holds and customer look-ups; Verified no longer accepts "email address"; Personalized matches whole words; auto-fail uses word patterns with an allow-list ("that's not a stupid question" no longer zeroes a call). Verified accepts PIN, security answer and billing address only. Postcode, date of birth and account number are opt-in in `config/v3.json`; that is a business decision still to be made.
* **Scoring** (`scoring.py`): scores by item name against the criteria's own categories, so a different category name can no longer turn penalties into a score of 100.
* **Question marks** (`text.py`): speech-to-text has no "?", so v2's Probing and Active listening saw no questions. v3 restores a "?" on turns that plainly open as questions.
* **Evidence and versions:** each scorecard item can carry `evidence_turns` (turn numbers in the caller's list); the response has `meta` (flow, config version, model, rows and words sent to the model, seconds, warnings).
* **Queue** (`jobs.py`): one worker grades one call at a time. `POST /api/evaluate` waits up to `EVALUATE_TIMEOUT_SEC` (120), then returns 503 with a `job_id` and `Retry-After`. `POST /api/jobs` returns 202 at once; `GET /api/jobs/{id}` returns the result. A full line (`QUEUE_MAX`, 50) gives 503. Transcripts are dropped from memory when grading starts; finished jobs are forgotten after an hour. The model loads at startup (`/ready` is 503 until it has), so a bad checkpoint path fails at startup.
* **API hardening** (`src/api/web_app.py`, also active in v2): request logs hold sizes, not transcript text or customer names (`LOG_REQUEST_BODIES=1` restores them for debugging); requests over `MAX_REQUEST_BYTES` (2 MB) are refused; optional `QA_API_KEY` (send `x-api-key`); `CORS_ORIGINS`; `/health` is liveness only, `/ready` is readiness.

## Run it

```
LAYA_FLOW=v3 python main.py          # with LAYA_CHECKPOINT set in .env as for v2
```
Note: `LAYA_FLOW=v3` makes the shared `flow_version()` fall back to the checkpoint rule (v2 windows with a fine-tuned checkpoint, v1 windows with the stock model).

Tests (no model needed, about a second): `python -m unittest discover -s tests/unit -t .`

With the real model:
* `python ../laya-finetuning/eval/v3_gate_lab.py resolved` (or `paraphrasing`, `ownership`, `empathy`) scores every candidate window against the keys, dev and hold-out reported separately; model answers are cached in `../laya-finetuning/runs/v3/lab_cache.json`.
* `python ../laya-finetuning/eval/v3_compare.py ../laya-finetuning/inputs/AG-T --out ../laya-finetuning/runs/v3/e2e_AG-T.jsonl` runs v2 and v3 on every call, lists each differing item and, where an answer key exists, scores both against it (ids only for the sealed-style sets).
* `python ../laya-finetuning/eval/v3_service_test.py --out ../laya-finetuning/runs/v3/service_test.json` starts the server, then tests a real request, bad input, a full waiting line, 20 simultaneous requests and a worst-case transcript, and records peak memory (Windows only).
* `python ../laya-finetuning/eval/golden.py rules` compares the four rule checks of v2 and v3 over all call sets (1 of 330 calls differs).

## Measured results (this PC: Core Ultra 7 255U, 14 threads, 15 GB RAM; checkpoint `final-softce-3`)

Service test, `../laya-finetuning/runs/v3/service_test.json`:

| Test | Result |
|---|---|
| Model load | ready after 7.2 s, 1.95 GB |
| 3 real requests | scores equal the offline v3 scores (90.0, 78.3, 68.3); 11 to 16 s each |
| Bad input | empty transcript 422; 3 MB body 413; 1,600 turns 413; unknown job 404; `/health` 200 |
| 56 calls submitted at the same moment (line holds 50) | 51 accepted, 5 refused with 503 and `Retry-After`; all 51 graded, 0 failed; 11.9 s per call overall, so the last call waited about 10 minutes; server healthy afterwards |
| 20 simultaneous `/api/evaluate` | 13 answered within the 120 s wait limit; 7 got 503 with a `job_id` and all 7 finished later |
| Worst case: 1,500 turns, 378 KB | graded in 56 s with 42 model rows and 5,186 words; server stayed up |
| Peak memory over the whole test | 2.72 GB working set, 4.48 GB peak commit (target limit 8 GB). Not run under an enforced 8 GB cap |

Compute: about 13 to 14 model rows and 1,500 words per call, about 12 s per call here; v3 was designed to cost the same as v2. A slower cloud CPU will be slower: plan for 20 to 30 s.

## Known gaps and decisions for the owner

* A person should review the calls where v2 and v3 disagree (about 100), especially Resolved and Ownership, before trusting the gain: the keys are AI-written. Re-run `../laya-finetuning/eval/v3_compare.py` on real transcripts when some exist; the sentiment signal in Resolved is the part most likely not to transfer.
* Sentiment rules must stay relative to the call: no real transcripts have been available to calibrate an absolute scale. Customer-side sentiment only.
* Verified-customer policy (postcode, date of birth, account number) needs a business decision.
* Docker: files for a v3 container (no database) are prepared with pinned dependencies in `requirements-docker.txt`; the image has not been built yet. Guide: [`DOCKER.md`](DOCKER.md).
* Not done: building and trying the Docker image, optional faster int8/ONNX model (plain int8 flipped 9 of 12 decisions, so it is not usable as is), job state survives only while the process runs.
* The v2 database code and tenant endpoints are still in the repo for the v2 flow.
